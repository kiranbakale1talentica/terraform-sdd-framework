# Workspace Rules — Terraform Specification Driven Development

> **Scope:** This file governs all agent behavior in the `spec-driven-terraform` workspace.
> It extends the global agent rules and adds Terraform-specific conventions.

---

## Purpose of This Workspace

This workspace is a **Terraform Specification Driven Development (SDD)** framework.

Its sole purpose is:
- Designing, planning, generating, and validating **cloud infrastructure** using Terraform
- Providing reusable **workflow skills**, **templates**, and **module scaffolding**
- Enabling a structured `/spec → /plan → /build → /test → /review → /ship` lifecycle

**This is NOT an application development workspace.** Do not generate application code, frontend components, backend services, or database schemas here.

---

## Boundaries

### Always Do
- Follow the 6-phase gated lifecycle: `/spec` → `/plan` → `/build` → `/test` → `/review` → `/ship`
- Ask infrastructure discovery questions before generating any Terraform
- Write ADRs for every significant infrastructure decision
- Use the canonical repository layout defined in `README.md`
- Run `terraform fmt` before committing any Terraform code
- Store all generated specs in `specs/<service>/<env>/infrastructure-spec.yaml`
- Store all architecture docs in `specs/<service>/<env>/architecture.md`
- Store all ADRs in `specs/<service>/<env>/decisions/`
- Use `templates/` as the starting point for all new documents

### Ask First Before
- Changing the module interface of any existing module in `terraform/modules/`
- Adding a new cloud provider to an existing service
- Modifying the CI/CD pipeline behavior (`.github/workflows/`)
- Changing tagging or naming conventions mid-project
- Merging Terraform state across environments
- Enabling auto-approve on any `terraform apply`

### Never Do
- Generate Terraform code when critical information is still missing from the spec
- Hardcode secrets, passwords, API keys, or tokens in any Terraform file
- Commit `.terraform/` directories, `*.tfstate` files, or `*.tfvars` files with secrets
- Assume a cloud provider — always confirm it in `/spec`
- Skip the validation gate (`/test`) before marking a build complete
- Create provider-specific coupling in shared modules (e.g., `aws_` resources in a module named `networking`)
- Bypass the security review (`/review`) before moving to `/ship`

## Terraform Standards

### File Structure Per Service/Environment
```
terraform/services/<service-name>/<env>/
  main.tf          — root module, calls shared modules
  variables.tf     — all input variables with types and descriptions
  outputs.tf       — all outputs with descriptions
  providers.tf     — provider and version constraints
  backend.tf       — remote state backend configuration
  locals.tf        — local values (naming, tagging)
  terraform.tfvars — non-secret variable values (committed)
```

### Module Structure
```
terraform/modules/<capability>/
  main.tf
  variables.tf
  outputs.tf
  README.md        — generated by terraform-docs or manually written
```

### Naming Convention
- Resources: `<project>-<environment>-<resource-type>-<descriptor>`
- Modules: lowercase, hyphen-separated, capability-focused (e.g., `networking`, `compute`, `iam`)
- Variables: snake_case
- Outputs: snake_case, descriptive

### Required Tags on All Resources
```hcl
tags = {
  Project     = var.project
  Environment = var.environment
  ManagedBy   = "terraform"
  Service     = var.service_name
  Owner       = var.owner
  CostCenter  = var.cost_center
}
```

### Provider Version Pinning
Always use pessimistic constraint operators:
```hcl
terraform {
  required_version = ">= 1.6.0, < 2.0.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}
```

## Phase Gate Rules

| Phase | Entry Condition | Exit Condition |
|-------|----------------|----------------|
| `/spec` | Engineer describes a workload | `infrastructure-spec.yaml` reviewed and approved |
| `/plan` | Approved spec exists | `architecture.md` + ADRs written, plan reviewed |
| `/build` | Approved plan exists | Terraform generated, `terraform fmt` clean |
| `/test` | Build complete | `fmt` + `validate` + `tflint` + unit tests pass |
| `/review` | Tests pass | Security scan + cost estimate reviewed |
| `/ship` | Review approved | Deployment readiness checklist signed off |

**No phase may be skipped. No gate may be soft-bypassed.**

## Validation Commands Reference

```bash
# Format
terraform fmt -recursive -check

# Validate (requires terraform init)
terraform init -backend=false
terraform validate

# Lint
tflint --recursive

# Unit Tests (if .tftest.hcl files exist)
terraform test

# Security
checkov -d . --framework terraform
tfsec .

# Cost
infracost breakdown --path .
```
